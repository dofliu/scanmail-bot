### 手邊就能做的小東西

| 項目 | 為什麼 | 規模 |
|------|------|------|
| **自動快門的門檻要看真機** | v3.22.0 的 `STEADY_MOVE = 0.012` / `STEADY_HITS = 3` 是**估的**：合成串流完全不會抖（位移恆為 0），在它上面調不出有意義的數字。取景畫面已經把當下的位移百分比顯示出來 —— 拿真機手持看幾秒，太少自動拍就把門檻放寬、拿著還在拍就收緊 | 看兩個數字 |
| **取景時的節流門檻要看真機** | 偵測間隔現在固定 350ms、取樣固定 640px 寬，是照「單張 100–300ms」估的。低階手機上可能還是會頓，高階手機則是浪費 —— 拿真實裝置量過再決定要不要改成看 `session.latest().ms` 自動調整。跟上面那項適合同一次量完 | 調參數 |
| **自動快門的偏好要能留過關機** | 現在記在 `studio.jsx` 的模組層變數（`autoShutterPref`），關掉 App 就回到預設的「開」。`SMNative.store` 已經在了（v3.17.0 / v3.21.0 兩次都用它），接上去就好；順手可以一併收掉其他同類的小偏好 | 接既有的儲存層 |
| **打碼 / 標註不跟著旋轉走** | 兩者都畫在「裁切之後」的畫面上，所以先框好再按旋轉，框會留在原本的相對位置、指到別的內容。裁切框與格子取景在 v3.10.0 / v3.16.0 已經各自解掉（`rotateRect` / `rotateFit`），這兩個是同一類問題還沒補。做法照抄 `rotateRect`：打碼是矩形可以直接用，方框 / 箭頭 / 螢光筆要對兩個端點各做一次同樣的映射，手寫則是對軌跡上的**每一個點**做（同一個映射，只是要跑一圈） | 一個晚上 |
| **一般文字不能轉角度** | v3.24.0 把浮水印的 `rotate` 從一般文字身上清掉了（它原本會讓文字莫名歪 30 度），所以現在非平鋪的文字一律是水平的。引擎本來就吃 `rotate`，要給的話就是面板上再一根滑桿 —— 但九宮格定位本來就是為了「按一下就對齊」而做的，先等真的有人想斜著放再補 | 加一根滑桿 |
| **文字圖層不能調順序** | 疊在後面的層畫在上面，順序就是新增的順序。要改順序現在只能刪掉重打。真的疊到重疊才會痛，六層以內多半各佔一個九宮格位置，先不做 | 兩顆上下移的鈕 |
| **標註的線寬不能調** | 現在固定 0.006×短邊。文件截圖夠用，但拿去標一張細節很多的圖時會太粗 —— 資料結構早就吃 `width`，缺的只是介面上的一根滑桿。等真的遇到再補，現在加是憑空猜使用者要什麼 | 加一根滑桿 |
| **螢光帶的粗細不能調** | 固定 0.036×短邊，是照「一行內文的高度」訂的。標題字比它高、註腳比它矮，都會蓋不準。跟上面那一項是同一根滑桿的問題，適合一起做 —— 引擎那一側 `width` 早就吃了 | 加一根滑桿 |
| **手寫的抽稀門檻是估的** | 相隔 < 0.004（畫面短邊的 0.4%）的點會被丟掉，是照「390px 寬的手機上約 1.5px」推的，沒有在真機上畫過。畫得慢的人會被抽掉太多點（線變得有稜有角），畫得快的人則是抽不掉。真機上寫幾個字看得出來 | 調一個常數 |
| **螢光筆的扶正門檻是估的** | 偏離水平 / 垂直 8° 以內會被扶正。8° 是「手拖過一行字大概歪多少」推的，沒有量過。太小的話手抖一下就不扶正，太大的話真的想斜著畫也會被拉平 | 調一個常數 |
| **「照片糊掉」的判斷** | v3.18.0 的重拍建議刻意沒收這一條 —— 量過了，用現有的梯度圖分不出來：一張清楚的空白紙 p95 梯度是 68，一張糊到看不清字的也是 68（`features()` 又先做過半徑 2 的模糊）。要做得先在 `features()` 留一份未模糊的高頻能量，或改量邊緣寬度 | 換一個量測方式 |

### 大的、要想清楚才動的

**裝置端 OCR** —— 掃描型 PDF 變成可搜尋、圖片轉文字，也能餵給表單填寫。
`doc-local.js` 現在會直接丟「這份 PDF 抽不到文字 —— 需要 OCR」，是程式碼裡自己承認的洞。
但成本要誠實看：tesseract.js 的中文語言包比英文大一個量級，辨識率也不如後端的 PaddleOCR。

- [x] **M1**：先做數字與英文（v3.26.0，`ocr-lite.js` + `doc-local.js` 的逐頁 fallback）。
      掃描型 PDF 不再丟「需要 OCR」，抽不到文字的**那一頁**改走 OCR，讀出來的行
      換算成 PDF 座標之後跟抽出來的走同一套段落還原。App 打包 +6.1MB
- [ ] **M2**：中文選配（語言包大、辨識率有落差，做成使用者自己選要不要下載）

**圖片轉文字的入口** —— 引擎那一側 `SMOcrLite.recognize()` 吃任何 canvas，
缺的純粹是介面：圖片工具裡沒有「這張圖轉成文字」這個動作，OCR 目前只有
掃描型 PDF 這一條路走得到。做的時候順手把 `digits` 模式接出來
（框一格金額、只讀數字），那個模式的引擎已經在了。

**OCR 的 render 寬度要拿真實掃描件重訂** —— `doc-local.js` 的 `OCR_RENDER_WIDTH`
目前是 1600。量出來的結果是：合成的 10pt 頁面在 1000px 就到頂（信心 95、全對），
595px 會掉到信心 84 而且多讀出一個原文沒有的句點，2000px 比 1000px 慢一倍卻沒有更準。
**1600 是留餘裕、不是量出來的** —— 合成頁面沒有雜點、沒有歪斜、沒有壓過頭的 JPEG，
而那三樣正是靠解析度換回來的。手邊有幾份真的掃描 PDF 之後，跑一次同樣的比較
（`npm run test:ocr` 裡那段 `byWidth` 直接改寬度就能重跑）再把數字定下來；
往下調到 1200 每頁大約省三成時間。

**文件轉檔的面板沒有介面測試** —— `mobile/test/studio.test.mjs` 130 條裡一條都沒有
走到轉檔面板，所以 v3.26.0 那則「第 N 頁是 OCR 認出來的」提醒只有一條 pytest
原始碼守門，沒有真的點過。`mobile/www/` 裡現在就有打包好的 OCR 資產，
補測試的話可以真的跑完整條路。

**OCR 沒有取消鈕** —— 一份 20 頁的掃描件大約要 15 秒以上，中途只能等。
進度是有的（`onProgress` 逐頁回報），缺的是「停」。

**Token 沒有撤銷機制** —— `/api/auth/logout` 只清掉 cookie，那張 Token 本身
到過期（24 小時）之前都還是有效的：被複製走的 Token 登出也叫不回來。
要做就是一份 jti 黑名單，或把 Token 綁一個可以遞增的 per-user 版本號
（後者比較省，不用存狀態）。`AUTH_SECRET_KEY` 換一把可以把**所有人**踢下線，
但那是全體、不是單一使用者。

**登入限流擋不住散在很多 IP 的攻擊者** —— v3.27.0 的限流按來源 IP 算，
一個 IP 五分鐘十次。要更嚴就得再加一層「同一個帳號被猜了幾次」的計數，
但那會變成一種把別人帳號鎖死的騷擾手段（知道帳號名就能讓對方登不進去），
所以要一起想清楚鎖定策略（漸進延遲通常比直接鎖定好）。

**`index.html` 的 `?v=` 從 v3.15.0 之後就沒動過** —— 所有 script 標籤上的
快取破壞參數都還是 `?v=3.15.0`，凍了十幾個版本。實務上靠 StaticFiles 的
ETag revalidation 補救，所以不太會真的讓使用者吃到舊 JS，但那個機制存在的
意義就是不要依賴 revalidation。做法：`build_mobile.py` 已經會讀 `main.py` 的
版號，讓它順手把 `?v=` 一起換掉，再補一條測試釘住「不准落後於 main.py」。

**次像素角點精修** —— 裝置端目前角點誤差約 2–6px（後端 v5 是 0.6px）。

偵測跑在 480px 工作解析度上，抓完直接放大回原圖。對「拉正」這個用途夠用，
真的要做就是在原始解析度上沿邊緣法線方向做拋物線內插 + 穩健直線擬合。
**等有真實照片的回饋再決定**，現在補是憑空優化。

### 2026/09/01 (v3.27.0 — 認證邊界：金鑰分離、登入限流、註冊閘門)

- **一把金鑰在做兩件事。** `ENCRYPTION_KEY` 同時加密存下來的 SMTP 密碼**和簽發
  身分 Token** —— 兩件威脅模型完全不同的事共用同一把 `sha256(secret)`。
  Token 改走加了標籤的雜湊（domain separation），兩把鑰匙位元組不同、
  拿到一把回推不出另一把；另外開 `AUTH_SECRET_KEY`，單獨換它就能把所有人
  踢下線，不必動 SMTP 那把。
- **用公開的預設金鑰又開認證，現在會拒絕啟動，不是印警告。** 那個字串就在
  `app/config.py` 裡，`ENABLE_AUTH=True` 疊在它上面等於任何讀過 repo 的人
  都能簽一張帶任意 `user_id` 的 Token。警告會被日誌淹掉，而**以為自己有保護
  比知道自己沒保護危險得多**。
- **`/api/auth/*` 原本完全沒有限流**，而八個功能 router 每一個都掛了
  `Depends(rate_limit)` —— 所以密碼可以無限次猜。微妙的地方是**直接重用
  `rate_limit` 修不了這件事**：它用 `X-User-Id` 當 key，而那個 header 是
  客戶端自己填的。對已登入的人當配額標籤沒問題，拿來擋猜密碼等於沒擋，
  每猜一次換一個 header 就換到新配額。所以登入 / 註冊另外掛一支
  **只認 `request.client.host`** 的限流器（五分鐘 10 次），並且有一條測試
  真的照攻擊的方式走：每次都換 `X-User-Id`，仍然要吃到 429。
- **註冊原本是完全開放的** —— 認證擋住了未登入的人，卻沒擋住「自己註冊一個」
  這條路。現在只開放給**第一個**帳號，或帶對 `REGISTRATION_TOKEN`。
  零設定的代價是「第一個搶到的人就是主人」，所以啟動時會把這個窗口還開著
  明確講出來。
- 同一片區域順手修的三件：①登入 cookie 的 `Secure` 原本寫死 `False`，
  旁邊一句「生產環境可設為 True」（也就是沒人會改），改成跟著請求 scheme 走、
  `COOKIE_SECURE` 可以蓋過。②「查無此人」原本約 6ms 就回，而密碼錯誤要跑
  十萬次 PBKDF2 約 68ms —— 從外面數毫秒就能列舉帳號，現在查無此人也照樣
  補算一次假雜湊。③`/health` 回的版號寫死 `3.15.0`，跟同一個檔案裡的
  真版號並存。
- 測試 +12（289 → 301）。**mutation 測試抓到三條「沒有真的在測那個修正」的測試**，
  而且是同一種錯：對著輔助函式斷言，而不是對著真正用到它的那條路。
  ①比 `_get_key() != _auth_key()` 只證明模組**算得出**兩把不同的鑰匙，
  不證明 `create_access_token` 用的是對的那把（改成簽一張真的 Token，
  要求 SMTP 那把解不開）。②直接呼叫 `_cookie_secure()` 抓不到呼叫點被改回
  寫死（改成讀真正的 `Set-Cookie`）。③時間那條的**斷言方向錯了** ——
  拿掉補算雜湊會讓「查無此人」變**快**，上界永遠不會紅。七個 mutation 現在
  全部咬得住。
- **刻意把 roadmap[0]（OCR M2 中文）往後挪**：M2 是大而不確定的增量
  （10MB 級語言包、離線版沒網路可下載、辨識率還沒跟後端 PaddleOCR 比過），
  而這幾件是一個晚上做得完、且「哪天對外開才會發現」的那種洞。

### 2026/09/01 (v3.26.0 — 裝置端 OCR M1：數字與英文)

- **「這份 PDF 抽不到文字 —— 需要 OCR」這句話不用再出現了**（英數的部分）。
  那是 `doc-local.js` 裡程式碼自己承認的洞：頁面上明明有字，只是那些字是像素。
  新的 `static/js/ocr-lite.js` 包住 tesseract.js（LSTM / WebAssembly），完全在裝置上跑。
- **沒有為 OCR 另外寫一套段落還原。** `fromPdf()` 本來就是吃「一堆帶座標的行」
  去還原標題、段落、項目符號，而 OCR 給的正好就是這個 —— 座標換算成 PDF 的
  左下原點、單位點之後，下游根本分不出這一頁是抽出來的還是認出來的。
- **判斷放在每一頁，不是整份文件。** 一份 PDF 常常是電子檔的正文加上掃描的附件，
  整份一起判會讓那些附件跟以前一樣讀不到。測試把一頁電子檔跟一頁掃描件合成一份，
  驗 `ocred` 回來是 `[2]`。
- **一個真的坑，一個自己嚇自己的。** 真的那個：tesseract.js 預設把 worker 跑在
  `blob:` URL 上，於是 emscripten 的 `scriptDirectory` 是空的，core 解不出自己
  `.wasm` 的相對路徑，直接炸 `Failed to parse URL`。`workerBlobURL: false` 修掉，
  順便留住比較小的分離式 core（2.87MB + 0.12MB，單檔內嵌版要 3.86MB）。
  假的那個：本來多寫了一層「把資產位置對 `document.baseURI` 解成絕對網址」，
  理由是「worker 裡的相對路徑是相對於 worker 自己，`langPath: 'vendor'` 會變成
  `vendor/vendor`」。**mutation 測試把那層拿掉，29 條全過** —— 去翻 tesseract.js
  的原始碼才發現它自己就會把三個路徑對 `window.location.href` 解過。那層已經刪掉，
  但它帶出來的測試留著（harness 刻意掛在子目錄底下），那個行為變了才會有人知道。
- **白名單不是過濾器。** 實測 `tessedit_char_whitelist` 套上數字之後，
  `INVOICE NO. AB-20260901` 變成 `0.-20260901` —— tesseract 會把每個字硬塞成
  最接近的白名單字元，不是把它丟掉。所以 `digits` 是呼叫端明講才用，永遠不是預設。
- **render 寬度是量出來的，而且第一次猜錯了。** 原本照「scale 1 的 A4 只有 595px 寬、
  10pt 內文大寫字高剩 7px」推出 2000px。實際跨五種寬度量同一頁 10pt 的合成掃描件：
  **1000px 就到頂**（信心 95、全對），595px 掉到信心 84 而且多讀出一個原文沒有的句點，
  2000px 比 1000px 慢一倍（625ms vs 298ms）卻沒有更準。定在 1600 是**留餘裕**——
  合成頁面沒有雜點、歪斜與 JPEG 壓縮痕跡，而解析度換回來的正是那三樣。
  這件事是估的不是量的，連同數字與重訂的作法都寫進註解與後續工作。
- **worker 全程共用一個。** 初始化是 ~0.5 秒的 wasm 編譯加 2.9MB 模型，
  一頁開一個的話 20 頁的文件光重複開關就花掉十幾秒。測試直接數 wasm 被抓幾次，
  要求剛好一次。
- **面板會說是「哪幾頁」用 OCR 認的**，不是只說「這份用了 OCR」——
  後者等於要使用者整份重讀。
- App 打包多 6.1MB（worker + SIMD-LSTM wasm core 2.9MB + 英文語言包 2.9MB）。
  語言包取 `4.0.0_best_int` 而不是完整的 `4.0.0`（10.7MB）：差 7.8MB，
  但對印刷體的金額與單號看不出辨識率差別。
- 測試 +37：新的 `npm run test:ocr`（29 條，跑真的 wasm，掃描件 fixture 是現做的
  canvas → JPEG → `imagesToPdf`，真的沒有文字層）加 8 條 pytest 接線守門。
  既有的守門測試自己抓到一個漏掉的東西 —— `sw.js` 的預快取清單少了新的 script。
- **mutation 測試這次真的有做事。** 除了確認該紅的會紅（`workerBlobURL` 拿掉整套掛住、
  逐頁判斷拿掉 2 紅、render 寬度改回 scale 1 是 3 紅），它另外抓出**四個沒人在守的決定**：
  一個是上面那層多餘的路徑解析（刪掉）；另外三個補上了該有的驗證 ——
  **行的順序**（少了左下原點的翻轉，整頁會顛倒過來，但每個字都還在，
  所以只驗內容的斷言一條都不會紅）、**混合文件裡標題的層級**
  （`OCR_CAP_RATIO` 只在「OCR 頁與電子頁共用同一個內文字級」的時候才有意義），
  以及**信心門檻**（補一張純雜訊的圖）。

### 2026/08/09 (v3.25.0 — 標註工具 M2：螢光筆 / 手寫)

- **標好的重點終於可以「刷」而不是「框」。** 一行字要標起來，以前只能框一個方框 ——
  框把整行圈住，卻沒有告訴人「這一行是重點」。螢光筆刷過去就是那個意思。
- **螢光筆跟「畫一條半透明色帶」的差別在合成模式。** 半透明疊色會把黑字一起洗淡
  （字變灰），`multiply` 只讓亮的地方染上顏色，**黑字仍然是黑的** ——
  螢光筆的重點是刷過去還讀得到。也因為這樣它不需要暈邊：暈邊是為了讓細線在同色
  背景上不消失，在螢光帶四周圍一圈黑框只會變成一個奇怪的色塊。
- **螢光筆一律畫在其他標註底下**，不管它排在陣列的第幾個。它是底色 ——
  排在箭頭之後畫，紅箭頭疊上黃螢光就變成橘的，那不是使用者畫過的東西。
- **平頭不是圓頭。** 真的螢光筆就是平的；圓頭會從拖曳的兩端各多蓋出半個帶寬，
  蓋到下一個字上 —— 等於使用者標到了他沒有標的東西。
- **拖歪 8° 以內會扶正。** 拖過一行字的手一定會歪個幾度，歪掉的帶子會從行首切到
  行尾的半個字高。超過 8° 視為「真的想斜著畫」，照拖的角度畫。
- **手寫存的是整條軌跡**（`points`），不是起點終點 —— 一條手寫的線本來就不是
  兩個端點描述得完的。畫的時候走「以原始點為控制點、相鄰兩點的中點為端點」的
  二次曲線，直接連折線在手機上看得出鋸齒。
- **抽稀在擷取的時候就做掉**（相隔 < 0.4% 的點丟掉，一筆上限 400 點）。
  `pointermove` 一秒進來幾十次，原封不動收下來的每一個點，之後每一次預覽都要再畫一遍。
- **顏色分兩組記。** 螢光筆有自己的一排亮色（黃 / 綠 / 藍 / 粉），因為深色 multiply
  下去會把字一起壓黑；反過來挑了螢光黃之後箭頭也跟著變黃就更看不到了。
- **拖到一半的示意改用 SVG。** 本來是一個 DOM 方框（箭頭拿一條虛線對角線代替），
  現在四種筆各畫各的 —— 手寫根本沒有方框可以畫。螢光筆的示意套用同一條扶正規則，
  拖的時候看到的角度就是放開之後的角度。
- +30 測試：引擎 13、介面 9、pytest 接線 2（其餘為既有測試改寫）。
  Mutation 檢查：`multiply` 換回一般疊色 1 條紅、拿掉螢光筆先畫的排序 1 條紅、
  平頭換圓頭 2 條紅、拿掉扶正 1 條紅、二次曲線換折線 1 條紅、拿掉手寫暈邊 1 條紅。
- 刻意沒做：螢光帶與筆畫的粗細滑桿、以及讓標註跟著旋轉走（打碼從 v3.12.0 就有
  同一個洞，兩件事屬於同一次改動）。都寫進「後續工作」。

### 2026/08/06 (v3.22.0 — 即時取景 M2：框穩了自己拍)

- M1 讓框在按快門前就跟著文件走，但**手還是得騰出來按快門** ——

- **`static/js/scan-live.js`**：穩定度判斷 + 自動快門

### 2026/08/06 (v3.21.0 — 伺服器位址存進原生儲存)

- 接續 v3.17.0 的簽名庫。同一個問題的另一半：App 的後端位址存在 `localStorage`，
  而那在 WebView 裡是快取不是儲存。使用者只是清了一次快取，
  App 就忘記伺服器位址、跳回設定畫面要人**重打一次 IP** —— 而位址通常記不起來
- 難處在**載入順序**：`config.js` 排在 `native.js` 之前，而且是同步讀取，
  載入的當下問不到非同步的 Preferences。作法是把它拆成兩段，而不是改整條載入鏈：
  - **開機（同步）** 照舊讀 `localStorage`。App 內它是原生儲存的鏡像，
    絕大多數時候兩邊一樣，所以 `apiBase` 一載入就有值，下游模組完全不受影響
  - **`ready()`（非同步）** 由 `native.js` 在啟動時 `await`，跟原生儲存對一次答案：
    鏡像被清掉了就把位址救回來、原生儲存還沒有就把舊位址搬過去（只發生一次）
- **順序才是重點**：`native.js` 先 `await SM_CONFIG.ready()`、之後才判斷要不要跳設定畫面。
  少了這個 await，位址雖然救得回來，設定畫面卻已經蓋上去了 —— 使用者看到的還是要重打 IP
- 位址因此有可能在載入**之後**才定案，`api.js` 不能再把它當常數抄走：
  加了 `onApiBaseChange` 訂閱與 `rebase()`。各 function 裡的 `${BASE}` 本來就是
  呼叫時求值的，但七個工具前綴（`imgBase` 這種）是載入時就先組好的字串，得一起換 ——
  漏掉哪一個，那一類工具就會在清過快取的裝置上打到 `https://localhost`
- `save()` / `clear()` 改成非同步（要等 Preferences 落地才重新載入頁面）。
  原生寫入失敗時退回 `localStorage` —— 存得不夠久，但至少這次設定沒有白費
- **網頁版與離線版一行都沒改到行為**：兩者根本沒有「要連到哪一台」的問題，
  `ready()` 直接 resolve，測試也釘住它們完全不去碰原生儲存
- 測試 +25，新的一支 `npm run test:config`。**每個情境都真的載入一次頁面**，
  用一段 prelude 在 `config.js` 之前佈置好旗標 / `localStorage` / 假的 `window.SMCap`，
  讓載入順序跟 App 裡一模一樣 —— 順序寫錯測試就會紅，那正是這件事最容易錯的地方。
  另外 2 個 pytest 防呆釘住接線：`native.js` 的 `ready()` 必須排在 `openServerSetup()` 之前、
  `api.js` 宣告的每個 `xxxBase` 前綴都要出現在 `rebase()` 裡

### 2026/08/02 (v3.17.0 — 簽名庫存進原生儲存)

- 簽名庫原本存在 `localStorage`。在 App 裡這不是「一個儲存位置」而是**會被清掉的快取** ——
  Android 的「清除快取」、系統回收儲存空間、部分 ROM 的省電清理都會把 WebView 的資料

- **`SMNative.store`**（`static/js/native.js`）：一層統一的「要留著的小資料存哪裡」介面。

  - 升級後第一次執行，`localStorage` 裡的舊簽名會自動搬進 Preferences（只發生一次）
  - App 內不再因為 `localStorage` 存不下就砍掉最舊的簽名 —— Preferences 容量大得多，

### 2026/08/01 (v3.16.0 — 取景跟著旋轉走)

- 承 v3.15.0 的格子內取景：構圖調好之後只要按一下旋轉，畫面就會跳掉。
  原因是對焦點存的是**原圖上的相對座標**，圖轉了它就指到別的內容 ——

  兩者不一致的話裁切框跟取景會在旋轉後各自跑到不同地方；測試直接拿一個沒有大小的
  裁切框跟 `rotateFit` 對答案，把這個約束釘住
  - `zoom` 是「相對於剛好填滿格子」的倍率，跟方向無關，原封不動帶過去
  - 沒動過取景的圖（`fit` 是 `null`）不會被硬塞一個 fit，維持原本一個像素都不變的路徑
- **拉正後取景歸零**：`deskewItem` / `undoDeskew` 把 `fit` 跟 `cropRect` 一起設回 `null`。
  透視校正會把整張圖重新映射，舊的對焦點指到的已經不是同一塊內容，
  留著只會讓拉正後的第一眼構圖是亂的

### 2026/07/28 (v3.15.0 — 拼貼的觸控取景與交換)

- 試用回饋：拼貼時圖片在格子裡的位置動不了，順序也只能靠重新加圖來排
- **格子內取景**：選了圖之後單指拖曳移動、兩指捏合縮放
  - 格狀版面（cover）會把圖裁切填滿，拖曳就是決定要露出哪一塊
  - 存的是相對值（縮放倍率 + 0–1 對焦點），縮圖上調完、原圖匯出構圖一致
  - 對焦點夾在「實際可動」的範圍內 —— 不夾的話手指會累積一段拖了卻不動的空行程，
    回拖時要先把那段還回來，感覺像卡住
  - **沒動過取景的圖走原本那條繪製路徑**，一個像素都不會變（既有輸出不受影響）
- **交換位置**：點「⇄ 交換」再點另一張，兩張對調
  - 沒有明確模式的話沒人猜得到「點 A 再點 B」會交換 —— 那本來就是「改選 B」
  - 畫布與縮圖列共用同一條 `pickIndex()`，兩邊行為一致；縮圖比在拼貼上點準得多
- 點選與拖曳共用同一塊畫布，靠 4px 位移門檻分辨；而且只有拖「已經選中的那張」
  才算移動，不然點旁邊的圖會把它撞位
- `touchAction: 'none'` 是必要的 —— 不擋掉的話瀏覽器會把拖曳與捏合當成捲動 / 縮放整頁
- `setPointerCapture` 加上 try/catch：合成事件沒有真的指標會丟 NotFoundError，
  而捕捉只是為了拖出畫布邊界時還收得到事件，抓不到不影響手勢

### 2026/07/28 (v3.14.0 — 裝置端邊界偵測 + 透視校正)

- 離線版本來只有自由裁切，真正「掃描」的那一半（自動抓紙張、拉平）一直長在後端。
  補上之後，「拍紙本 → 自動抓邊 → 拉正 → 存 PDF」整條線第一次能完全不連網跑完
- **偵測只留一條路：梯度導向的 Hough 直線偵測**。後端 v5 跑七種策略再評分，
  瀏覽器沒有那個預算；選直線是因為文件的邊本來就是直線，而且直線由整條邊投票決定，
  **角被手指擋住不影響**（後端當初得補凸包才解決）
  - 一般 Hough 每點要投 180 個角度；利用「梯度方向垂直於邊」，每點只投自己的角度

  「往內側偏移」的梯度，木紋桌面之類的假邊會被淘汰）、最弱邊乘法門控。
  那些權重是 22 個案例的基準測試磨出來的，憑感覺重寫只會退步
- **透視校正走 WebGL** —— canvas 2D 只做得到仿射。一支 fragment shader 逐像素反推
  來源座標，雙線性取樣是 GPU 順便給的。拿不到 WebGL 就退回「切細格、每格仿射近似」
- **輸出尺寸用 Zhang–He 法反推真實寬高比**，不然斜拍的 A4 拉正後會系統性被拉扁
- 信心 < 0.45 不自動裁切，改提醒「沒把握」請使用者確認 —— 對齊後端的門檻。
  亂裁一通比不裁更糟，使用者不會發現
- 拉正是破壞性的（換掉原圖），所以留了「還原原圖」，並清掉已經沒有意義的裁切框
- 測試方式：**合成有標準答案的「拍紙本」影像**，量角點誤差。正對 / 斜拍 / 旋轉 14° /
  角被手指擋住 / 昏暗低對比都要 < 10px；另外放了該失敗的場景，確認它老實回報低信心
- 過程中抓到兩個只有靠特定驗法才看得見的 bug：
  - **WebGL 輸出上下顛倒** —— 一開始的「線有沒有變垂直」驗不出來，因為垂直線翻過來
    還是垂直線。改用四個顏色不同的象限做恆等變換才現形
  - **warp 直接回傳 WebGL 畫布** —— 一張 canvas 只能有一種 context，呼叫端的
    `getContext('2d')` 會拿到 null，後面所有合成整條斷掉。改成搬回 2D 畫布再回傳

### 2026/07/28 (v3.13.0 — 簽名 / 印章)

- 這個平台的用途是寄公文、合約、收據，而這些文件常常就差一個簽名。
  原本的流程是「印出來 → 簽 → 再掃一次」，現在手指簽一次存起來，之後拖到定位就好
- **手寫簽名存的是筆畫的點而不是像素**：
  - 蓋進 PDF 輸出的是向量路徑 —— 放大不糊、列印跟原生文件一樣銳利，一枚只佔幾 KB
  - 曲線用「相鄰兩點的中點連成二次貝茲」；PDF 沒有二次貝茲運算子，換算成三次，
    兩邊算的是同一條線，所以畫面上看到的就是蓋出來的
  - 存進 localStorage 前跑 Ramer–Douglas–Peucker 簡化，手指畫出來的上百個點砍到剩幾十個
- **匯入圖片當印章**：拍一張紙上的簽名或關防，用亮度當透明度去掉白底。
  「保留原色」留住紅色關防，「轉成墨色」把太淡的原子筆整個換色。自動裁掉四周空白
  - 蓋進 PDF 走影像 XObject + SMask 軟遮罩，中間是真的透明，不會把底下的字蓋掉
- **蓋章的座標**是這次最容易寫錯的地方：`/Rotate` 是交給檢視器轉的，內容串流的座標
  不會跟著轉 —— 使用者在轉過向的頁面上點右下角，直接寫進去會蓋到左上角。
  四個方向各一組變換矩陣，另外處理 MediaBox 原點不在 (0,0) 的檔案
  - 原本的內容包進 `q…Q` 再接簽名（它可能留下改過的座標系或顏色）
  - `/Resources` 常被好幾頁共用，一律複製一份再改，蓋一頁不會動到別頁
- 圖片端：簽名畫在文字圖層之上 —— 簽名是最後蓋的那一道
- PDF 頁面擺放時單獨把那一頁畫大一點（`pdfPageImage`），縮圖列的 200px 對不準簽名欄的橫線
- 測試方式：**把蓋完的頁面畫出來數墨點**。放在哪一個象限就只有那一個象限的深色像素變多，
  矩陣寫錯的話墨會出現在別的象限，逃不掉
  - 傾斜方向也用同一招驗：拿一枚墨集中在上半部的簽名，轉 90° 後重心該跑到右邊。
    第一版寫成負角（以為外層的上下翻轉會反轉旋轉方向），畫面上往右傾、蓋出來卻往左傾，
    就是被這條抓出來的
